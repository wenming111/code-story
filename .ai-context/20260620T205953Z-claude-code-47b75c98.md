## 为什么 PR 总结不该是 git hook 做的
这点我们之前掰扯过,结论很明确:
- **commit 时 PR 还不存在**(PR 是 push 之后在平台上创建的),git hook 在本地提交那刻**根本不知道自己属于哪个 PR**。
- squash/merge 在网页点的,本地 hook 也不触发。

所以 PR 维度**天生不适合写入时(hook)做**,设计上是**读取时**派生:
> agent 读代码 → blame 到 commit → 反查它属于哪个 PR → 把那个 PR 的 commit 范围(`base..head`)里各 commit 的 `.ai-context` 摘要**现场聚合**成一段 PR 叙事 → 用完即弃,不写 git。

而且还定了**阶梯升级**:默认只看 commit 级,不够时才抬到 PR 级。

## 现状一句话
- ✅ 有:**每个 commit 的对话 + 摘要**(写入侧,hook)
- ❌ 没有:**PR/MR 整体总结**(读取侧,按需 agent 合成)——还没做,因为读取侧整体暂缓了

如果你现在想把 PR 总结做出来,那就是**正式开聊读取侧**了——而且 PR 维度有个绕不开的硬骨头:**commit→PR 的反查要对接平台 API(GitHub / 内部 Bits)**。要不要现在就开读取侧、从 PR 总结这条线切入?
